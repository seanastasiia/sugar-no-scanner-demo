# Sugar.no Live Scanner: team handoff

This document is the engineering and product entry point for continuing the Latvia scanner proof of concept. The repository is the source of truth. Chat history is not required.

## Start here

1. Open the [live scanner](https://sugar-no-scanner-demo-production.up.railway.app) on an iPhone and allow camera access.
2. Read the root [README](../README.md), especially `Current state`, `Product rules`, `Catalog`, `Supabase`, `Railway and release`, and `Privacy`.
3. Run the deterministic Shelf and Checkout scenes before testing arbitrary products.
4. Read [Week-one lessons and guardrails](week-one-lessons.md), [Product QA](product-qa.md), [Acceptance matrix](acceptance.md), [Latvia coverage plan](latvia-coverage-plan.md), and [Bugs](../Bugs.md).
5. Treat `GET /api/health` and the newest file in `docs/test-runs/` as the current deployed evidence. Do not rely on screenshots alone.

## What the prototype currently proves

- Safari can start a camera-first scan without a shutter action.
- Gemini can name several distinct readable products in one shelf or checkout frame.
- Repeated facings of the same SKU are grouped as one product.
- Exact source-backed protein and total-sugar data can produce `Great fit`, `Moderate fit`, or `Low fit`.
- Results remain held while the user reads and are ranked best-fit-first.
- A trusted physical shelf price can be compared with an exact, current Barbora offer.
- Raw frames are transient and are not stored by this application.

The prototype does not guarantee exact visual recognition for every Latvian grocery product. Catalog nutrition coverage and visual top-1 recognition are separate metrics. Ambiguous variants must fail closed instead of borrowing another SKU's nutrition or price.

## Access checklist

Invite team members to services instead of copying credentials into chat, email, tickets, or source control.

| Service | Access needed | Why |
| --- | --- | --- |
| GitHub repository | `Write` for contributors, `Maintain` for the technical owner | Branches, pull requests, Actions, releases |
| Railway project | Project member access | Deployments, logs, variables, health checks |
| Google Cloud / AI Studio project | Least-privilege project access for the technical owner | Gemini quota, billing, API-key rotation |
| Supabase project | Developer access only if the team will use managed catalog/analytics data | Migrations, seed, server-side data inspection |

Do not reveal or rotate production secrets during onboarding. Railway already holds the runtime values. A developer should create their own `.env.local` from `.env.example`; production credentials remain in the service secret stores.

Required Railway variables are documented in `.env.example` and the README. The sensitive values are:

- `GEMINI_API_KEY`
- `SUPABASE_SERVICE_ROLE_KEY`

Neither may use a `NEXT_PUBLIC_` prefix. If access must be revoked, remove the team member from each service and rotate only the affected credential through the owning provider and Railway.

## Local setup

Requirements: Node.js 22 or newer.

```bash
git clone https://github.com/seanastasiia/sugar-no-scanner-demo.git
cd sugar-no-scanner-demo
cp .env.example .env.local
npm install
npx playwright install webkit
npm run dev
```

The deterministic Shelf and Checkout scenes work without external credentials. Live recognition needs a developer Gemini key. Camera testing on a physical iPhone needs HTTPS; use the production deployment or a secure development tunnel approved by the team.

## Architecture in one pass

1. The browser gets the camera stream with `getUserMedia`, waits for a stable frame and sends one bounded JPEG at a time.
2. `POST /api/recognize` asks Gemini for visible package identities, normalized boxes, optional barcode and tightly gated shelf-price evidence.
3. The server matches identities against the curated catalog and the checked-in Barbora food/nutrition snapshots. Nutrition is never generated by Gemini.
4. Live camera returns the first identity result quickly. `POST /api/resolve-products` performs bounded, image-free Barbora/Open Food Facts enrichment in the background.
5. The UI groups repeated facings, holds the result, ranks rated products and leaves unresolved products as `Needs nutrition label`.
6. `POST /api/events` accepts metadata only. Image-like fields and data URLs are rejected.

Key implementation locations:

- Scanner UI and camera lifecycle: `src/components/scanner-app.tsx`
- Recognition provider and prompts: `src/server/recognition.ts`
- Exact Barbora matching and nutrition: `src/server/barbora-*.ts`
- Scoring and presentation: `src/lib/scoring.ts`, `src/lib/match-presentation.ts`
- Upload tiling and merge behavior: `src/lib/upload-scan.ts`
- Generated catalog snapshots: `data/*.generated.json`
- Reproducible database schema: `supabase/migrations/`
- Browser acceptance coverage: `tests/e2e/scanner.spec.ts`

## Product trust rules that must remain intact

- Product identity is not the same as verified nutrition.
- Gemini may recognize packaging, but it may not invent protein, sugar, a price, a retailer SKU, or a Sugar.no fit.
- A fit requires source-backed protein and total sugar on a consistent per-100 basis.
- A Barbora action requires an exact SKU. Possible matches never receive a retailer link or comparison claim.
- `Cheaper at Barbora` requires a trusted physical shelf price, a current exact Barbora price, and proof that the online price is lower.
- Commercial availability never changes the independent fit or ranking.
- Avoid `bad`, `unhealthy`, or food-shaming language.
- Raw images must remain transient. Do not add frame storage or image analytics without a new privacy decision.

## Catalog refresh

The deployed app uses checked-in, versioned snapshots so startup and recognition do not depend on live crawling.

```bash
npm run catalog:sync
npm run catalog:sync:barbora-index
npm run catalog:sync:barbora-nutrition
npm run catalog:validate
npm run catalog:validate:barbora-coverage
```

`catalog:sync:barbora-nutrition` is resumable and rate-limited. Review the generated diff, source timestamps, adult/non-food exclusions, duplicates and supported-category floors before committing it. Never treat the raw sitemap count as nutrition or recognition coverage.

Supabase is reproducible with:

```bash
npx supabase login
npx supabase link --project-ref <project-ref>
npx supabase db push
npm run supabase:seed
```

## Release procedure

1. Merge the reviewed change into GitHub `main`.
2. Confirm `npm run verify` and the relevant WebKit scenarios passed on the exact commit.
3. Let the GitHub-linked Railway service deploy, or use the documented Railway CLI procedure when a direct release is necessary.
4. Wait for the Railway build and health check to complete.
5. Confirm `/api/health` reports `status: ok` and the expected commit.
6. Run the affected flow on the public URL, separately from automated tests.
7. Add a dated record under `docs/test-runs/` and update `Bugs.md` for any defect found or fixed.

Do not call a release complete after a local screenshot or local tests alone.

## Product acceptance for a new team member

On an iPhone Safari session:

1. Open the live URL and allow camera access.
2. Confirm the camera fills the primary surface and recognition starts without taking a photo.
3. Open Shelf demo and verify several distinct products, fit-colored markers and the ranked product sheet.
4. Verify the deterministic cheaper-Barbora example shows both prices and an exact retailer action.
5. Open Checkout demo and verify three rated identities on the real checkout-belt image.
6. Scan repeated facings of one product and confirm they are grouped.
7. Scan an unsupported or ambiguous product and confirm the app requests a nutrition label instead of inventing a fit.
8. Tap `Scan again` and confirm the held result clears before a new result appears.

## Recommended ownership after handoff

- One engineering owner for releases, Gemini quota/billing and production incident response.
- One catalog/data owner for Barbora refreshes, source provenance and coverage measurement.
- One product owner for fit language, retailer claims, investor demo scope and acceptance decisions.
- Pull-request review required for recognition thresholds, prompts, scoring, privacy, source matching and price claims.

## Suggested next work

1. Build a ground-truthed Latvia set from real snack and dairy shelves, then report identity recall and exact-SKU precision separately.
2. Add provider cost/latency telemetry without raw images or package OCR in analytics.
3. Move recurring catalog refresh to an auditable scheduled data pipeline with diff review and source freshness alerts.
4. Decide whether production recognition should remain multimodal LLM-based or add barcode/OCR/on-device CV before expanding categories.
5. Define retailer partnership and affiliate rules before presenting online purchase as a revenue stream.

These are next-stage decisions, not claims that the current proof of concept already recognizes every Latvian product.
